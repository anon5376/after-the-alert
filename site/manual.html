Incident response manual

Name the owner, preserve the evidence, and identify what actually ran. Then follow the vendor’s current guidance and keep receipts for the recovery.

For solo operators and small agencies coordinating work across client sites, packages and hosting accounts. Everything here is free, including the scripts and checklist. Voluntary donations do not unlock anything.

Know the limits. This is a dated public-source guide, not continuous monitoring, a scan or a security certification. It does not establish whether your systems were compromised. A responsible technical owner must adapt and execute the response. Get qualified incident-response help when compromise is suspected or the scope exceeds that owner’s ability. Unknown stays unknown.

01 / Start

Start with a record, before changing the system.

Possible LiteLLM exposure? Do not start Python or pip in that environment. The reported payload can run on interpreter startup. Read the LiteLLM section first.
  1. Assign an owner. Name who can authorize and perform changes for each asset. Record the decision, time and business impact. Coordinate urgent containment with evidence preservation; do not postpone containment while waiting for a perfect inventory.
  2. Preserve what you can safely preserve. Retain existing deployment records, artifact identifiers, relevant logs and provider notices before rebuilding or deleting anything. Store evidence with restricted access. Record who collected it and when. Keep credential values out of the checklist.
  3. Identify the deployed and executed artifact. Record the installed version, package source or image digest, build/download time, deployment time and execution times where relevant. A dependency declaration or mutable image tag alone cannot identify what ran.
  4. Read the original notice again. Open the vendor source linked in the matching section. Record its update time and the guidance you used. This snapshot can become stale.
  5. Let the technical owner execute the response. Record containment, updates, credential revocations and rebuilds separately. Use the current vendor procedure and a trusted environment. Do not treat a successful update as proof that exposed credentials were revoked.
  6. Verify and hand over. Check the deployed artifact and application behavior with independent evidence. Assign every unresolved question an owner and a next check. Use the closure record.

One record per asset

Identity
Asset, environment, client or project reference, technical owner.
What ran
Installed version, artifact origin and digest or package build, download/build/deploy/execution times.
Basis
Original advisory URL, access time, applicable interval or incident condition.
Action
Decision, executor, start and completion times, rollback plan, receipt location.
Remaining gap
Unknown fact, evidence needed, responsible person, next check time.

02 / Runtime

PHP: compare the running build.

PHP’s 21 October advisory covers CVE-2026-109618 and CVE-2026-109619. It identifies web-serving installations as at risk, with mod_php the highest-risk configuration. The upstream fixed releases are:

Upstream floors for these two vulnerabilities
BranchFixed release
8.28.2.35
8.38.3.36
8.48.4.27
8.58.5.12

Earlier releases within those branches need attention. PHP also supplied minimal source backports for 7.4, 8.0 and 8.1. Distribution packages may carry backported fixes without matching these upstream numbers: obtain the distributor’s advisory and exact package-build receipt.

Record the runtime serving requests, including every worker or replica. A CLI version, control-panel setting or successful build alone does not establish the version serving production traffic. After the owner updates and restarts or redeploys as required, retain a runtime receipt and application smoke-test results.

Sources: PHP’s 21 October advisory, out-of-memory corruption advisory, stale global state advisory. Snapshot: 22 October 2026.

04 / Release artifacts

LiteLLM: do not start the affected interpreter.

The vendor identifies all seven PyPI wheels for version 1.107.0 and affected Docker Hub/GHCR artifacts. It reports that the public source tag was clean. A clean repository therefore cannot establish that an installed release artifact was clean.

Do not run Python or pip to check the version. The reported payload executes at Python interpreter startup without a LiteLLM import. Have the technical owner inspect an offline, read-only copy from a trusted environment.
Vendor-reported windows on 21 October 2026, UTC

Affected tags included v1.107.0, latest, main-latest and main-stable. Preserve artifact identity and download, build, deploy and interpreter-start times. Cached artifacts may run later than the distribution window.

Use the current vendor response procedure for containment, credential revocation and a clean rebuild. Missing local markers do not prove absence of exposure. A metadata check cannot determine which credentials were read or whether they were used.

05 / Credentials

Railway: track revocation separately from deployment.

Railway’s 21 October disclosure says an unauthorized party may have accessed encrypted environment variables and obtained decrypted contents for some. It recommended rotating stored variables and private-registry credentials for all users as a precaution. This is not confirmation that every customer was breached.

Inventory credential types and owning services without copying secret values into the record. The technical owner should follow the latest notice, replace affected credentials through their issuing providers, update dependent services and confirm the old credentials are revoked. Preserve provider receipts with secret values removed.

Verify both halves: the application uses the replacement successfully, and the issuer records the old credential as revoked. A new deployment proves neither on its own. Keep the remaining exposure question open if the available evidence cannot answer it.

Deployment status is time-sensitive. The last status retained for this guide was 22 October at 00:22 UTC: work to restore builds continued. That is a stale snapshot, not a current claim that deployments are paused or restored. Check the live status before planning work.

Sources: Railway’s security disclosure and Railway’s live status page. Research date: 22 October 2026.

06 / Migration

Zeabur: restore before you call a backup usable.

Zeabur’s 17 October announcement schedules a wind-down. It describes unauthorized access on 14 October to internal systems and some customer services.

Announced service deadlines
DateWhat changes
1 December 2026Dedicated-server renewals stop; servers shut down at individual expiry. Shared-cluster services pause, with manual restart available for backup.
31 December 2026Final dedicated-server and shared-cluster shutdown.

Use the actual server expiry as a planning constraint. The final shutdown date does not guarantee service until then. Data-deletion, final-export and support-closing dates were still unfinalized in the announcement.

Record databases, files, configuration, domains and external dependencies. Choose a destination with the technical owner. Restore into an isolated destination, check record counts and representative files, and run application smoke tests. Record the backup time and the data lost or changed since it. An export file’s existence proves only that a file exists.

Before cutover, agree how to handle new writes, verify the restored application and keep a rollback plan. Retain restore and cutover receipts. Mark migration complete only when the owner accepts the restored service and outstanding data gaps.

Source: Zeabur’s founder announcement, incident account and service shutdown timeline. Snapshot: 22 October 2026. Restore and acceptance steps are this guide’s operational checklist.

07 / Verification

Close the action with evidence. Keep the unanswered question.

Separate the action from the conclusion. “Updated” describes work. “The production runtime reports the fixed build at this time” describes evidence. Neither establishes that an earlier compromise never occurred.

What to retain for each action
ActionIndependent receiptFunctional check
Update or rebuildProduction artifact digest or exact package/runtime build, collection time and source.Representative requests, login, background work and critical integrations, where applicable.
Credential replacementIssuer’s revocation record for the old credential; replacement identifier with values removed.Dependent service succeeds using the replacement.
MigrationRestore log, backup timestamp, destination identity and data-comparison results.Representative reads and writes on the restored application, then agreed cutover checks.

Obtain the receipt from the running system or issuing provider, independently of the change command’s success message. Have another person review it when available. A solo operator can use a separate read-back and record that no second person reviewed it.

End the record with the owner’s decision, evidence locations, unresolved questions and next check time. Keep “exposure unknown” if logs, artifact identity or execution history are missing. Do not turn an empty search result into a clean bill of health.

09 / Take it with you

Free downloads. Read-only checks.

Read each script before running it. Use a trusted machine. These tools collect or compare narrow observations; they do not patch systems, revoke credentials, assess compromise or certify recovery.

PHP version comparison · Node.js

Compares a version you supply with this snapshot’s upstream floors. It does not connect to a server or identify its live runtime. Distribution backports need separate evidence.

node check-php-version.mjs 8.3.35

The example uses an invented observation. PHP 8.3.35 is below the listed 8.3.36 upstream floor.

LiteLLM metadata inspection · shell

Lists matching metadata-directory names and marker filenames immediately inside one directory. It reads no file contents and starts neither Python nor pip. Run it against an offline, read-only copy from a trusted environment. Supply the physical path to that copy’s site-packages directory; symlink paths are rejected.

bash inspect-litellm-metadata.sh /path/to/site-packages

The check is not recursive and does not inspect container artifacts. Local metadata can be missing or altered. A result cannot rule out an affected artifact or prior execution.

Response checklist · plain text

A fill-in record for ownership, artifact identity, actions, receipts and unresolved questions. Store completed copies privately. Never put credentials or other secrets in them.
